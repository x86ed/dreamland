## Context

Iktomi is the free-form/broad-routing agent Janus dispatches to when a request has no OpenSpec context to route against (`.claude/agents/iktomi.md`, and the equivalent five platform templates under `internal/scaffold/templates/agents/`). Its three responsibilities today (per the currently-installed `.claude/agents/iktomi.md`, which is the stale, pre-`claude-code-parity` text — see below):

1. Handle the request directly, using good judgment.
2. If the work turns out to fit a specialized agent's role partway through, hand off directly to that agent — not limited to a single fixed target, unlike the narrow pipeline agents.
3. Otherwise, report completion or blockers to Janus when done.

The still-open `claude-code-parity` change already modified step 3 on two of six platforms (`internal/scaffold/templates/agents/{claude-code,github-copilot}/iktomi.*`, both already committed to this branch — confirmed by reading the live template files, not just that change's tasks.md) to: hand off to `phobetor` for validation if the work touched files, otherwise report to Janus as before. That change explicitly scoped the other four platforms (`cursor`, `codex`, `kiro`, `antigravity`) out as noted follow-up work (`openspec/changes/claude-code-parity/specs/janus-router-agent/spec.md`: "this requirement applies to them too... but bringing their templates into compliance is unfinished follow-up work, not done here").

The user's ask ("iktomi should always handoff to phobetor") replaces the file-changed/no-file-changed branching with a single unconditional rule, and this change applies it uniformly across all six platforms — which also resolves `claude-code-parity`'s four-platform gap as a natural side effect of simplifying the rule (dropping the conditional makes the six-platform edit trivially uniform; there's no longer a reason to have left four platforms out).

**A second, independent source of drift, not fixed by this change**: this repo's own live, self-hosted `.claude/agents/iktomi.md` (what Janus in *this* repo actually dispatches against right now) does not yet contain even `claude-code-parity`'s conditional split — it still reads the original, unmodified "Otherwise, report completion or blockers to Janus when done." `claude-code-parity`'s task 9.4 ("Commit the merged `.claude/agents/` ... Blocked on user confirmation — not yet done") is the existing, tracked task for re-syncing this repo's live agent files from the templates; it hasn't run yet. This change does not duplicate or preempt that task — see Decisions below.

## Goals / Non-Goals

**Goals:**
- Make Iktomi's post-completion hand-off to `phobetor` unconditional: always, regardless of whether the completed work touched files.
- Apply the same unconditional rule uniformly across all six platform templates, closing both `claude-code-parity`'s two-vs-six-platform gap and its file-changed/no-file-changed conditional in the same edit.
- Keep Iktomi's other two responsibilities (direct handling, mid-task redirect to a clearly-fitting specialist) and its broad-routing capability completely unchanged.
- Keep `phobetor` itself completely unchanged — it already handles hand-offs from any source generically; nothing about its own instructions needs to change for this.

**Non-Goals:**
- No change to `phobetor`'s pass/fail/spec-defect routing, tools, or responsibilities.
- No change to how Iktomi decides whether a request is free-form (its dispatch-trigger criteria in the `janus-router-agent` requirement are untouched).
- No change to Iktomi's mid-task redirect capability (responsibility 2) or its "broad routing capability" framing — those remain, unrestricted, for the case where the work turns out to fit a specialist *before* Iktomi's own turn is complete. This change only fixes what happens *after* Iktomi's own work is done.
- No re-sync of this repo's live `.claude/agents/iktomi.md` (or any other live platform agent file) — that is `claude-code-parity`'s task 9.4, already tracked and explicitly gated on user confirmation before it commits anything. This change's implementer edits templates only, same as `claude-code-parity` and `phantasos-agent-lifecycle-routing` both did before it; the eventual re-sync run will pick up both changes' template edits together, whatever order they land in.
- No new CLI commands, no Go source changes — this is agent-instruction content only, same shape as the `phantasos-agent-lifecycle-routing` precedent.

## Decisions

**Template-file prose edit, not a graph-structural edit via `hypnos-serve`.** Two mechanisms exist in this codebase for expressing a routing edge: (a) hand-editing the canonical "hand off directly to `X`" sentence directly into an agent's template/instruction file (the convention `phantasos-agent-lifecycle-routing` and `claude-code-parity` both used for this exact kind of change), and (b) mutating the live workflow graph through `hypnos-serve`'s interactive/`apply-plan` mode, which reads/writes the *live installed* platform agent directories (`internal/workflowgraph.Import`/`Render`, driven by `platformAgentDirs` in `render.go`) and auto-generates a terse canonical sentence ("Once your work is complete, hand off directly to `X`.") from a `RoutesTo` edge. Mechanism (b) operates on live install directories, not on `internal/scaffold/templates/`, and its auto-generated sentence is deliberately generic — it would flatten Iktomi's existing fuller prose (the "if the work turns out to fit a specialized agent's role partway through" nuance) rather than integrate with it. This change is scoped to the *source-of-truth templates* (mechanism (a)), matching both directly-relevant precedents for touching Iktomi's own hand-off text.

**Keep the canonical `hand off directly to \`phobetor\`` substring intact, but hand-author the surrounding sentence per platform.** The workflow-graph importer's `handOffPattern` regex (`internal/workflowgraph/import.go`) matches `hand(?:s)? off directly to \`([a-z0-9-]+)\`` anywhere in a sentence, not the sentence verbatim — so the exact backtick-quoted substring stays parseable/consistent with the graph tooling's conventions even though the wording around it is written by hand, matching how `claude-code-parity`'s existing (still-live) template text already does this.

**Blockers still report to Janus; only a completed turn always routes to `phobetor`.** The user's phrasing ("always hand off to phobetor... once its work is done") is specifically about the completion path. A blocked turn (Iktomi can't proceed, or the next step needs broader context only Janus has) has nothing for `phobetor` to validate — `phobetor` runs tests and checks spec scenarios against completed work, it has no mechanism for resolving "I'm stuck." This mirrors the existing shape of `nyx`/`morpheus`, both of which have one fixed deterministic completion edge *and* a separate, unchanged "escalate ambiguity to Janus" path — not one rule trying to cover both cases.

**Applies to all six platforms in one pass, not just the two `claude-code-parity` already touched.** Considered keeping this change scoped to `claude-code`/`github-copilot` only (mirroring `claude-code-parity`'s stated scope exactly) and leaving `cursor`/`codex`/`kiro`/`antigravity` as a separate follow-up, same as that change did. Rejected: removing the conditional makes the edit identical in shape across all six platforms (one sentence, no branching) — splitting it into "two platforms now, four later" would recreate exactly the kind of drift this change exists to remove, for no benefit. All six templates already share the same per-platform structure this change touches (a short numbered/paragraph list of Iktomi's three responsibilities); the edit is mechanical repetition, not new design work per platform.

**This change's delta spec modifies the same `janus-router-agent` requirement `claude-code-parity` also modifies, and is written as a complete, order-independent replacement.** OpenSpec's `## MODIFIED Requirements` convention captures the full replacement text for a named requirement, not a line-diff — so this change's requirement text is written to be correct as a final state regardless of whether `claude-code-parity` archives before or after it (see Risks). No attempt is made here to sequence or depend on `claude-code-parity`'s archival; that reconciliation, if any conflict exists at archive time, is `baku`'s job when either change closes.

## Risks / Trade-offs

- [Risk] `claude-code-parity` (still open) also carries a `## MODIFIED Requirements` delta for this exact requirement (`janus-router-agent`: "Janus routes free-form requests to Iktomi, and Iktomi can route back or onward"), describing the two-platform conditional split. If `claude-code-parity` archives before this change, the base spec will briefly reflect the conditional split before this change's own archival replaces it with the unconditional rule — a normal, sequential base-spec update, not a conflict. If this change archives first, `claude-code-parity`'s still-open delta will describe a state this change has already superseded; whoever archives `claude-code-parity` second needs to notice its Iktomi/Phobetor delta is now moot and drop or reconcile it rather than silently reintroducing the conditional. Flagged here explicitly so it isn't a silent surprise at archive time — not resolved in this change, since resolving another change's delta isn't this change's authority.
- [Risk] This repo's own live `.claude/agents/iktomi.md` won't reflect either this change or `claude-code-parity`'s Iktomi work until `claude-code-parity`'s task 9.4 (blocked on user confirmation) runs. Until then, Janus in this repo keeps dispatching against the older, unmodified Iktomi text. Accepted — not this change's task to force that confirmation or commit.
- [Risk] Routing every Iktomi completion through `phobetor`, including turns with no file changes, means `phobetor` will sometimes be invoked with "nothing to test, nothing to check against a spec scenario" (pure investigation/Q&A turns). `phobetor`'s own instructions ("Run go test..."; "Check each completed task against its corresponding spec scenario") already tolerate a no-op-clean pass implicitly (no tests broken, no scenario to fail) — this isn't a new failure mode `phobetor` needs new instructions for, but it does mean `phobetor` sees more turns with nothing to actually verify. Accepted trade-off, consistent with the user's explicit "always" requirement; not addressed by adding new logic to `phobetor` (kept unchanged, per Non-Goals).
