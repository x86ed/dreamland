## Context

`dreamland init` scaffolds five agents per platform (`orchestrator`, `spec-writer`, `implementer`, `tester`, `pr-closer`) from templates embedded in the Go binary (`internal/scaffold/templates/agents/<platform>/`), and separately wires four lifecycle CLI commands (`version-bump`, `coauthor`, `transition-log`, `test`) into each platform's `SessionStart`/`Stop` hooks (`internal/scaffold/templates/hooks/bindings/<platform>/`). This change adds a fifth lifecycle command, `dreamland commit`. Today the `orchestrator` agent has generic `tools: Read, Bash` and prose instructions but no enforced contract. Hook-driven identity/telemetry (`dreamland coauthor`, `dreamland telemetry write`) only fires once per session, so a session that hands off across multiple agents records only the first agent's identity for the whole session.

Three gaps beyond the router itself motivate the rest of this change: `implementer` goes straight from spec to code with no enforced test-first step and the workflow is treated as one linear pipeline even though real usage isn't linear; free-form requests with no OpenSpec context have no agent to land on; and the agent roster itself has no feedback loop — nothing analyzes git history/token burn/turn duration to say which agents need tuning, nothing authors a new agent when a gap is found, nothing retires one that's no longer earning its keep. This change addresses the first two by adding `nyx` (acceptance-test writer) and `iktomi` (free-form fallback) and by making the router's routing table explicitly two-flow rather than linear, and addresses the third by adding a trio of agent-roster-maintenance agents — `zhougong` (analytics), `hypnos` (agent-authoring), `mengpo` (agent archival) — plus moving the router role itself from `hypnos` to `janus`, since `hypnos` is needed for its new role.

This change touches all six platform template sets (Claude Code, Codex CLI, Cursor, Kiro, Antigravity, GitHub Copilot) plus their hook bindings, and changes the shape of two existing specs (`agent-scaffolding`, `dev-workflow-hooks`) while adding three new capabilities, so a design doc is warranted.

## Goals / Non-Goals

**Goals:**
- Replace `orchestrator` with `janus` as the router, on every platform, with a frontmatter/instruction contract that marks it as router-only.
- Give Janus a narrower tool binding than the other nine agents so it cannot itself edit specs, tests, code, or agent definitions.
- Give Janus an explicit routing table across three tiers: `/opsx:*` commands (lifecycle-specific), `/route` (generic — Janus decides), and one explicit per-agent command each (the caller decides, Janus still performs the hand-off).
- Make every agent's hand-off deliberate: direct to a fixed next agent when the step is deterministic, through Janus when it requires judgment or the work has reached a terminal point — not an implicit free-for-all, and not a mandatory round-trip through Janus for every hop either.
- Document each agent's tool bindings as an explicit, enforceable three-tier matrix (read-only/dispatch, full-edit, write-only-no-edit) rather than implicit per-template convention.
- Make implementation routing genuinely non-linear: Janus picks, per task, between a direct-implementation flow (`morpheus` → `phobetor`) and an acceptance-test flow (`nyx` → `morpheus` → `phobetor`).
- Give free-form requests with no OpenSpec context somewhere to land: `iktomi`, selected by Janus only when no specialized agent matches.
- Close the agent-roster feedback loop: `zhougong` analyzes git history/token burn/turn duration and writes tuning/new-agent reports; `hypnos` authors new agents (across all platforms, registered with Janus) from those reports or a direct request; `mengpo` archives or deletes agents no longer needed.
- Reuse the name `hypnos` deliberately, for a role that is a natural fit once the router moves elsewhere: Hypnos is father of the Oneiroi in Greek myth, so having Hypnos *author* new Oneiroi-style agents (rather than route between them) is more mythologically apt than its original placement as router.
- Make `dreamland coauthor` and `dreamland telemetry write` fire on every agent handoff (not just once per session) so git identity and telemetry always reflect the currently active agent/model — uniformly, across all ten agents, including the three agent-roster-maintenance agents.
- Make every commit message include a token-usage report, alongside the existing `Co-authored-by:` trailer — this doubles as `zhougong`'s primary data source.
- Guarantee that every agent turn and every agent-to-agent transition produces a commit, even when the agent itself never explicitly runs `git commit`.
- Make the semantic version track the work automatically: patch by default on every agent turn, minor once per new OpenSpec change or branch, major when a change is finalized with a **BREAKING** marker — without requiring a human to remember to run `dreamland version-bump` themselves.

**Non-Goals:**
- Not building a new orchestration engine, state machine, or persistent routing history — Janus routes using the same "read `openspec status`, decide, delegate" pattern the orchestrator already used.
- Not migrating or deleting pre-existing `orchestrator.*`/`spec-writer.*`/`implementer.*`/`tester.*`/`pr-closer.*` files from repos that already ran `dreamland init` — this is additive scaffolding, same as any other template change.
- Not changing how `coauthor` and `telemetry write` derive identity/model info — this change only extends `coauthor --trailer`'s message content and adds one new command (`dreamland commit`) that reuses the existing prepare-commit-msg hook rather than duplicating its logic.
- Not implementing agent-handoff hooks for GitHub Copilot beyond the existing documented stub (its hook API remains undocumented).
- Not building a rich commit-squashing or history-rewriting story for the resulting checkpoint commits.
- Not merging `nyx`'s test-writing role into `phobetor`'s validation role or vice versa.
- Not forcing every implementation task through the acceptance-test flow — `nyx` is skipped for mechanical/internal tasks.
- Not defining a follow-up flow after `iktomi` (whether its changes always get `phobetor`-validated) — an open question, not a decision this change locks in.
- Not adding any new `dreamland` CLI commands for `zhougong`/`hypnos`/`mengpo` — all three operate by reading/writing files and running `git`/`gh` via their `Bash` tool, using data already produced by existing hooks (`Tokens:` trailers, `.dreamland/transition.log`). If that proves insufficient in practice, a dedicated `dreamland report`/`dreamland archive-agent` command is a future enhancement, not part of this change.
- Not building enforcement that stops `hypnos` from authoring a badly-scoped agent, or `mengpo` from archiving one still in use — both are judgment-driven, same as Janus's own flow-selection heuristic; a human reviews the resulting diff before it merges, same as any other agent's output.

## Decisions

**Rename in place, don't version — and add five genuinely new agents, one of them reusing a name freed up by another rename.** `orchestrator.*` → `janus.*`, `pr-closer.*` → `baku.*`, `spec-writer.*` → `phantasos.*`, `implementer.*` → `morpheus.*`, and `tester.*` → `phobetor.*`, all in the template source tree; the installer writes only the new names going forward, and none of the five old templates are kept alongside their replacements. Five templates are added fresh — `nyx.*`, `iktomi.*`, `zhougong.*`, `hypnos.*`, and `mengpo.*` — none a rename of anything. `hypnos.*` is the one subtlety: earlier in this change's own design process the router was going to be called Hypnos; that plan changed (see below), so by the time this change is implemented there is no "old `hypnos.*`" file to rename from — the router's file is `janus.*` from the start, and `hypnos.*` is authored fresh for its agent-authoring role. Rationale: each renamed agent is a drop-in replacement with identical responsibilities to its predecessor; the five new agents fill genuinely new roles that didn't exist in the five-agent set.

**The router moves from `hypnos` to `janus`; `hypnos` is reused for agent-authoring, not retired.** Janus (Roman god of doorways, transitions, and duality — literally depicted with two faces looking in opposite directions) is a better fit for "the thing every request passes through before going one way or another" than Hypnos (god of sleep) ever was. Freeing the name lets `hypnos` take a role that fits it better: Hypnos is the *father* of the Oneiroi (Morpheus, Phobetor, Phantasos) in Greek myth, so having Hypnos author new Oneiroi-style agents is thematically closer to the myth than having Hypnos route between agents it didn't create. Rationale: this is a deliberate, one-time name reuse, not a pattern to repeat — it's called out explicitly (here and in the `agent-scaffolding` capability) precisely because reusing a name for a different role is unusual and could otherwise read as an error.

**Router annotation is a frontmatter field plus a leading instruction block, not a new schema.** For Claude Code/Copilot (YAML frontmatter with `tools:`), add `role: router` to frontmatter and open the instruction body with a fixed "You are a pure router. You never edit files, write code, or write specs yourself." paragraph. For Cursor (`.mdc`) and Kiro (plain markdown) which don't have a `role` frontmatter convention, the same marker goes in the instruction body only. For Codex (`.toml`) add `role = "router"` as a top-level key alongside `name`/`description`. Rationale: reuses each platform's existing agent-definition format instead of inventing a cross-platform schema.

**Tool binding is a three-tier matrix, not binary.** Most agents are either read-only/dispatch (`janus`, `phobetor`, `baku` — `Read`, `Bash` only) or full-edit (`phantasos`, `nyx`, `morpheus`, `iktomi`, `hypnos` — `Read`, `Edit`, `Write`, `Bash`). `zhougong` and `mengpo` don't fit either: both need to create new files (a report; an archive-manifest entry) but neither should make targeted edits to another agent's existing content, so both get `Write` without `Edit`. Rationale: a binary matrix would force `zhougong`/`mengpo` into either "can edit anything" (too permissive — an analytics agent has no business editing a spec file) or "can't create its own report" (breaks the agent's entire purpose); the third tier expresses the actual constraint precisely.

**Routing table lives in Janus's own instructions, not in a separate config file.** The mapping (`/opsx:propose`, `/opsx:explore` → `phantasos`; `/opsx:archive` → `baku`; `/opsx:apply` → Janus decides per task between `nyx` and `morpheus`; no OpenSpec context → `iktomi`; agent-roster-maintenance requests → `zhougong`/`hypnos`/`mengpo`) is written directly into each platform's `janus.*` prompt body. Rationale: these slash commands are themselves static per-platform files; a separate routing-config file would be a second source of truth that can drift.

**`/opsx:apply` routes through Janus rather than to one fixed agent, because the workflow genuinely isn't linear.** Not every task needs an acceptance test written first, so `/opsx:apply` delegates to `janus`, which applies the flow-selection heuristic below per task, rather than jumping to one hard-coded implementer-role agent.

**Janus's flow-selection heuristic: route to `nyx` for new observable behavior, straight to `morpheus` otherwise.** If a task implements new behavior described by a spec scenario (`WHEN`/`THEN`) with no covering test, Janus delegates to `nyx` first; if the task is mechanical (rename, config/template edit, refactor with no behavior change) or a covering test already exists, Janus delegates directly to `morpheus`. This is a heuristic in Janus's prose, not a hard rule enforced by tooling.

**Agent-roster-maintenance requests (`zhougong`/`hypnos`/`mengpo`) are a separate branch of Janus's routing table, not folded into the implementation flows.** "Tune the agents," "add an agent for X," and "remove the unused agent Y" are requests *about* the agent roster, not tasks the roster works on — they don't have a `phobetor`/`baku` finalization step the way implementation work does. Rationale: keeping them as a clearly separate branch (rather than, say, treating a `zhougong` report as a "task" that flows through `nyx`/`morpheus`/`phobetor`) avoids conflating two different kinds of work that happen to both go through the same router.

**New slash command name: `/route`, plus one explicit command per agent (nine, up from six).** `/route` is the generic entry point that invokes Janus directly for requests that don't map to an existing `/opsx:*` command, including free-form requests that end up at `iktomi`. `/phantasos`, `/nyx`, `/morpheus`, `/phobetor`, `/baku`, `/iktomi`, `/zhougong`, `/hypnos`, `/mengpo` are explicit, named entry points: each tells Janus to route directly to that agent, still going through Janus so `dreamland coauthor`/`telemetry write` fire normally. `/hypnos` is worth calling out specifically: it invokes the agent-authoring agent, not the router — a caller who remembers "Hypnos used to be the router" needs to notice the rename; there's no backward-compatible shim for this, consistent with every other rename in this change being **BREAKING**.

**Hand-offs are direct when the next step is deterministic; Janus is only in the loop for the entry point, judgment calls, and terminal reports.** Earlier drafts of this change required every hand-off — even "implementation done, go validate" — to round-trip through Janus. That's not how the underlying workflow actually behaves: `nyx`→`morpheus`, `morpheus`→`phobetor`, `phobetor`→`baku`/`morpheus`/`phantasos`, and `hypnos`→`phobetor` are all fixed, single-outcome (or agent-determined-outcome) next steps with nothing for a router to decide — routing them through Janus added a hop that served no purpose beyond uniformity. So this change draws the line at determinism: an agent hands off *directly* when the next agent is fixed, and reports to Janus only when the next step requires broader judgment (`morpheus` escalating genuine ambiguity) or the work has reached a natural stopping point with no fixed continuation (`baku` closing a change, `iktomi` finishing free-form work, `zhougong` finishing a report, `mengpo` finishing an archive). Rationale: this keeps Janus meaningful as a *decision point*, not a mandatory relay for every hop — a router that mediates deterministic hand-offs isn't routing, it's just adding latency, and it dilutes what "goes through Janus" actually signals (a judgment call happened) once most traffic through it is mechanical pass-through anyway.

**Hand-off text is rewritten in `implementer.*`/`morpheus.*` and `tester.*`/`phobetor.*` (not just Janus), on all six platforms; `nyx.*`, `iktomi.*`, `zhougong.*`, `hypnos.*`, and `mengpo.*` each get a hand-off line written fresh.** An audit of the current templates found `implementer` escalates ambiguity with "ask the spec-writer to clarify" and `tester` reports failures with "report ... to the implementer" — direct agent-to-agent references that, under this change's model, turn out to be *correct* for the deterministic cases (impl-bug failures really should go straight back to the implementer role) but were never distinguished from the judgment-call cases, and fired no per-hand-off identity/telemetry hooks (that only ran once per session, before this change's `dev-workflow-hooks` extension). This change keeps the direct edges where they're genuinely deterministic, routes everything else (ambiguity, terminal reports) through Janus, and — separately — makes the coauthor/telemetry hooks fire on every hand-off regardless of which agent initiates it, which is the part that was actually missing.

**Iktomi and the agent-roster-maintenance trio (`zhougong`/`hypnos`/`mengpo`) get broad routing capability — the same fan-out as Janus — instead of being confined to narrow fixed edges.** The narrow-edge model fits `nyx`/`morpheus`/`phobetor` well because their work is genuinely pipeline-shaped: one deterministic input, one (or a small fixed set of) deterministic output(s). It doesn't fit `iktomi`, `zhougong`, `hypnos`, or `mengpo`: free-form coding can turn into anything; an analytics report can point at any agent needing attention; authoring or retiring an agent can have knock-on effects anywhere in the roster. Rather than force these four into an ever-growing list of special-cased fixed edges as new patterns are discovered, this change gives them the same broad dispatch capability Janus has — they hand off directly wherever their own work points, and report to Janus only when it doesn't. This also formalizes the Janus↔Iktomi relationship as genuinely bidirectional: Janus dispatches free-form work to Iktomi at the entry point, and Iktomi can dispatch onward to a specialist or back to Janus, not just terminate at a fixed report-back. Rationale: these four agents' defining trait is that their work is *not* pipeline-shaped — modeling them with the same narrow-edge mechanism as the TDD pipeline would either be wrong (missing real edges) or would require the edge list to keep growing indefinitely; broad routing matches what they actually do.

**GitHub Copilot requires the full hand-off graph declared structurally, in frontmatter (`agents:`), because that platform can't rely on prose alone the way Claude Code can.** VS Code's Copilot agent framework needs each agent's subagent-invocation permissions declared upfront in its own file header. This change declares exactly what the prose-level model above says: `morpheus`→`phobetor`, `phobetor`→{`baku`, `morpheus`, `phantasos`} as narrow edges; `iktomi`/`zhougong`/`hypnos`/`mengpo` each get all nine other agents, matching `janus`'s own fan-out; `phantasos`/`nyx`/`baku` list only `janus`. Rationale: this is the same graph every other platform's prose already describes — Copilot isn't a special case of the architecture, it's just the platform that needs the architecture written down structurally instead of only in prose. Granting every agent full access to every other agent would have made the frontmatter declaration meaningless as a permission boundary; matching it to the real graph (narrow where the work is narrow, broad where it genuinely is) keeps it a real capability list.

**The `hooks:` field, unlike `agents:`, is identical on all ten agents — `coauthor`, `telemetry-write`, `commit`, `version-bump` — because identity/telemetry/history-capture/versioning aren't tiered the way routing is.** `agents:` legitimately varies per agent (a narrow pipeline agent shouldn't be able to invoke everything; that's the point of declaring it). `hooks:` has no equivalent reason to vary: every agent's turn needs its git identity set, its token usage surfaced in the commit trailer, its cycle captured as a commit, and the version bumped, regardless of whether that agent is the router, a narrow pipeline agent, or a broad-router. This is the same "identical across every agent, no special-casing" principle the `dev-workflow-hooks` capability already establishes for Claude Code's `PreToolUse`/`SubagentStop` bindings — GitHub Copilot's per-agent `hooks:` field is that same guarantee, expressed the way Copilot's schema requires it (declared on each agent, since there's no shared binding file), not a different or weaker one. Rationale: normalizing this into one fixed four-item list, rather than letting it vary, removes an entire class of mistake (an agent template that's missing `commit` and silently produces no checkpoint commit for its turns, or missing `version-bump` and silently under-versions its work) — there's no legitimate reason for any agent to have a different `hooks:` list than any other.

**Version bumping gets three distinct triggers, each owned by a different point in the workflow, not one hook that tries to infer intent.** Patch is the default, per-turn case: bound to the same `SubagentStop`/`Stop` events as `coauthor`/`telemetry-write`/`commit`, so it needs no new trigger mechanism — it rides the infrastructure this change already built for per-turn hooks. Minor (new change or branch) is owned by `phantasos`, since it's the agent that actually runs `openspec new change` — rather than trying to detect "a new change happened" from a generic session/turn hook, the agent that causes the event triggers the bump directly, immediately after the causing action. Major (breaking) is owned by `baku`, since it's the agent that finalizes a change and already has to read `proposal.md` to confirm the task list is complete — checking for a **BREAKING** marker at that point costs nothing extra and is the last reasonable checkpoint before the version ships. Rationale: each trigger is placed where the triggering event is naturally observed, rather than centralizing version-bump logic somewhere that would need to infer these three cases indirectly.

**Phobetor's failure branch distinguishes an implementation bug from a spec defect.** A validation failure isn't always the implementer's fault — sometimes the spec scenario itself was wrong or ambiguous, and the fix belongs in `phantasos`'s domain, not `morpheus`'s. `phobetor` determines which case it is and hands off directly to the appropriate agent — this determination is Phobetor's own judgment about the failure, but the *destination* for each of the two outcomes is fixed, so both hand-offs are still direct, not routed through Janus. Rationale: forcing every failure through `morpheus` regardless of cause was a real gap in the original two-outcome design; fixing it doesn't require Janus's involvement because "which of two fixed destinations" is exactly the kind of determination an agent can make about its own output without needing a router's broader context.

**Agent-handoff hooks use each platform's sub-agent lifecycle event where one exists; otherwise Janus invokes the CLI commands itself.** For Claude Code: bind `dreamland coauthor` and `dreamland telemetry write --tool claude-code` to `PreToolUse` (matcher: `Task`) for handoff-start, and to `SubagentStop` for handoff-complete, in addition to the existing `SessionStart`/`Stop` bindings. For platforms without an equivalent sub-agent hook event, Janus's own instructions direct it to run both commands as an explicit step immediately before and after each delegation.

**`dreamland telemetry write` needs no code changes; `dreamland coauthor` gets one addition.** `coauthor --trailer` gains one new step: after appending the `Co-authored-by:` trailer, it reads the current turn's telemetry data and appends a `Tokens: input=<n> output=<n> cached=<n> total=<n>` line, or silently omits it if unavailable.

**Token-usage report rides the existing `prepare-commit-msg` hook rather than a new one.** One hook, one file write, one code path.

**Checkpoint commits are a new, separate command (`dreamland commit`) bound to `Stop` and `SubagentStop`, not folded into `coauthor` or `test`.** `--reason turn-complete` at `Stop`, `--reason handoff` at `SubagentStop`. Both stage everything (`git add -A`) and shell out to `git commit`, so the trailer and token report land on checkpoint commits for free via the existing `prepare-commit-msg` hook.

**Checkpoint commits stage everything unconditionally (`git add -A`), not just source files.** A checkpoint's job is to make sure no work is lost at a turn/handoff boundary.

**`zhougong` reads existing hook output rather than requiring a new telemetry pipeline.** Every data point in a `zhougong` report — commit counts, token totals, turn timing — is already produced by `dreamland coauthor`/`telemetry write`/`transition-log`. Rationale: building `zhougong` on top of data these hooks already write means no new instrumentation is needed; the analytics layer is a pure consumer of the lifecycle-hooks capability this change already extends.

**`mengpo` defaults to archive, not delete.** Moving a retired agent's files to `internal/scaffold/templates/agents/_archive/<platform>/` preserves its content and instruction history; hard-delete only happens on an explicit instruction. Rationale: agent retirement is a judgment call that's easy to get wrong (an agent that looks unused this week might be needed next sprint); archiving is cheap insurance, and the `.dreamland/archived-agents.md` log makes either action auditable regardless of mode.

## Risks / Trade-offs

[Janus template drifts across six platforms since the routing table and router-only framing are duplicated prose in each template, not a shared source] → Mitigation: tasks.md includes a review step that diffs the routing table text across all six `janus.*` files after editing.

[Non-Claude platforms rely on Janus "remembering" to invoke `coauthor`/`telemetry write` around each delegation, which is weaker than a hook guarantee] → Mitigation: documented as a known gap in the modified `dev-workflow-hooks` spec; `SessionStart`/`Stop` hooks still provide a session-level fallback.

[Patch-bumping on every sub-agent turn (not just once per session) means a single user-facing task can burn through many patch versions in one sitting — a task with five hand-offs produces five patch bumps] → Mitigation: this is the explicit trade-off of "every agent turn bumps patch by default" — patch versions are cheap and meant to be granular; if this proves too noisy in practice, the existing `version-bump --patch`'s "no-op if `git diff <last-tag>..HEAD` is empty" behavior already prevents a bump when a turn produced no code changes, which covers the most common case of a wasted bump (a read-only or routing-only turn).

[The two new marker files (`.dreamland/change-bumps` for minor, the **BREAKING**-marker scan for major) are new state to keep correct — a bug in either could silently skip a bump or double-bump] → Mitigation: `.dreamland/change-bumps` follows the exact same pattern as the already-existing `.dreamland/branch-bumps` marker (append-and-check-membership), so it's not a new mechanism, just a second instance of one already in production; the **BREAKING** scan is a simple grep-equivalent check `baku` performs once per change finalization, not a new stateful marker at all.

[Repos that already have an `orchestrator.*` file end up with both `orchestrator.*` and `janus.*` after upgrading, which is confusing] → Mitigation: `dreamland init` output already reports `installed:`/`skipped:` per file.

[`dreamland commit` running `git add -A` can sweep up files the agent didn't intend to commit yet] → Mitigation: explicit trade-off — checkpoints favor never losing work over commit hygiene; ordinary commits can be amended/squashed/reordered later.

[A high-frequency session with many handoffs produces a noisy git history of checkpoint commits] → Mitigation: the fixed `chore: <reason> checkpoint (<agent-name>)` subject format makes these filterable; squashing before opening a PR is `baku`'s existing responsibility.

[Telemetry data needed for the `Tokens:` report line may not be available at `prepare-commit-msg` time] → Mitigation: silent omission rather than blocking the commit.

[Rewriting hand-off text touches ten files' worth of prose across six platforms — easy to miss one and leave a stale direct reference] → Mitigation: tasks.md includes a grep-based verification step confirming no agent file references a legacy name or a peer agent by name as a hand-off target.

[Someone who only skims prose (not the full "deterministic vs. judgment" requirement) could assume every hand-off should go through Janus, since that was true for most of this change's own drafting history, and then "fix" a direct edge into an indirect one, adding pointless round-trips] → Mitigation: the deterministic-vs-judgment split is stated as its own named requirement in the `janus-router-agent` spec (not buried in agent-specific scenarios), with the full edge list spelled out once rather than scattered; the GitHub Copilot `agents:` frontmatter also makes the deterministic edges machine-checkable, not just prose-describable, which catches drift on that platform even if the prose does get "corrected" incorrectly.

[Routing some hand-offs directly instead of through Janus means Janus's own instructions no longer describe the full observable flow of a task — someone reading only `janus.*` won't see the `morpheus`→`phobetor`→`baku` chain, only that Janus dispatched the entry point] → Mitigation: acceptable trade-off — Janus's routing table still documents that these hops happen and roughly in what order (see the "Janus's instructions define a routing table" requirement's note that downstream hops are direct), even though Janus itself doesn't mediate them; a full task's flow is still traceable by reading the chain of individual agents' hand-off instructions, just not from Janus's file alone.

[Reusing the name `hypnos` for a completely different role than it had earlier in this same change's history is confusing — anyone who saw an earlier draft of this proposal will expect `/hypnos` to be the router] → Mitigation: called out explicitly in the proposal, this design doc, and the `agent-scaffolding` spec, not left as an implicit fact to notice; there is no transition period where both meanings are valid — by the time this change is implemented, `hypnos` only ever means the agent-authoring agent.

[`zhougong`'s tuning suggestions and `hypnos`'s resulting new agents could be low-quality if the heuristics in their prose are too vague — a report could recommend a redundant or badly-scoped agent] → Mitigation: both operate as advisors/authors whose output is reviewed like any other agent's — `zhougong`'s report is a suggestion, not an automatic trigger; `hypnos` only authors an agent when explicitly asked (directly, or by a user acting on a report's recommendation) via Janus, never autonomously.

[`mengpo` archiving or deleting an agent that's still referenced somewhere (a stale doc, a user's habit of typing `/some-agent`) breaks that reference] → Mitigation: default-archive keeps the file recoverable; the `.dreamland/archived-agents.md` log makes it discoverable why a command stopped working; this is the same class of risk as deleting any other file and is treated the same way (git history is the ultimate recovery path).

[Introducing `nyx`/`iktomi`/`zhougong`/`hypnos`/`mengpo` grows the agent roster from five to ten — more files to keep in sync, more surface for the hand-off/tool-matrix rules to drift on] → Mitigation: this is the explicit point of `zhougong`/`hypnos`/`mengpo` existing — the roster is meant to grow and shrink over the project's life, and this change is what makes that sustainable (analytics before adding, archival before the roster grows unbounded) rather than ad hoc.

## Migration Plan

1. Rename template files and update frontmatter/instructions (all six platforms): `orchestrator`→`janus`, `pr-closer`→`baku`, `spec-writer`→`phantasos`, `implementer`→`morpheus`, `tester`→`phobetor`. Add the five new templates (`nyx.*`, `iktomi.*`, `zhougong.*`, `hypnos.*`, `mengpo.*`) from scratch (all six platforms).
2. Rewrite hand-off language in `morpheus.*` and `phobetor.*` (all six platforms) per the deterministic-vs-judgment split: direct hand-offs for fixed next steps, Janus for ambiguity; write the five new agents' hand-off lines the same way, giving `iktomi`/`zhougong`/`hypnos`/`mengpo` broad routing capability rather than a fixed edge list.
3. Write Janus's routing table covering all nine other agents, both implementation flows, the `iktomi` fallback, and the `zhougong`/`hypnos`/`mengpo` agent-roster-maintenance branch.

## Open Questions

- Should `/route` eventually replace `/opsx:*` as the only public entry point, or do both stay directly user-invocable long-term? Left open for a follow-up change once usage patterns are observed.
- Should the manual-invocation convention for non-Claude platforms be revisited if/when those platforms document a sub-agent lifecycle hook? Tracked as a future enhancement, not blocking this change.
- Does `iktomi`'s output ever get routed to `phobetor` for validation, or does it stand entirely outside the spec/test/validate lifecycle? Left open — this change only defines that `iktomi` hands off to Janus when done.
- Should Janus's flow-selection heuristic eventually be informed by something more concrete than prose judgment — e.g. a `tasks.md` annotation the spec-writer sets? Left open for a follow-up change if the heuristic proves unreliable.
- Should `zhougong` run on a schedule (e.g. weekly) rather than only on demand via `/zhougong`? This change only wires the on-demand path; a scheduled trigger would need a new hook binding and is left as a future enhancement.
- Should `hypnos`-authored agents require a `phobetor`-style validation pass on the new template files themselves (e.g. confirming the tool matrix is internally consistent) before being registered with Janus? Left open — this change specifies what `hypnos` produces, not an automated check on its output.
